# Data Model: Sponsors Page

## Stored data (on the `sponsors` branch)

### Entry file — `data/entries/<id>.json` (one per sponsor)

| Field | Type | Required | Rules |
|-------|------|----------|-------|
| `id` | string | Yes | 12 lowercase hex characters; equals the file name stem; set by the server |
| `name` | string | Yes | Trimmed, "1–60 characters, no control characters"; rendered as plain text |
| `image` | string | No | `<id>.<webp|png|jpg>` when a picture was submitted (server-assigned from the detected type); list parser also accepts any name matching `^[a-z0-9][a-z0-9._-]{0,63}\.(png|jpe?g|webp)$` |
| `link` | string | No | Absolute `https` URL, ≤ 200 characters, no embedded credentials |

No amounts, tiers, dates, usernames, or donation references are stored in entry files.

### Generated list — `data/sponsors.json`

| Field | Type | Rules |
|-------|------|-------|
| `version` | integer | Must be `1`; any other value → treated as unreadable by the wallet |
| `sponsors` | array of entries | Same fields as an entry file; oldest first (by when each entry file was first added); never hand-edited, regenerated by the `build-sponsors-index` workflow |

### Sponsor image — `data/images/<id>.<webp|png|jpg>`

WebP, PNG or JPEG (extension assigned by the server from the detected type) ≤ 200 KB, ≤ 512×512 pixels (size checked by the server; pixel dimensions by the branch workflow). Older or hand-added images may be PNG/JPEG within the same limits.

## Submission (request to the server; never persisted by the server)

| Field | Type | Required | Rules |
|-------|------|----------|-------|
| `type` | `add` \| `remove` | Yes | Selects add or removal pull request |
| `name` | string | Yes (add only) | Same rules as entry `name`; not used for `remove` |
| `link` | string | No | Same rules as entry `link`; ignored for `remove` |
| `image` | file | No | WebP, PNG or JPEG ≤ 200 KB with a matching signature (wallet resizes and re-encodes first); ignored for `remove` |
| `txid` | string | Yes | DGB transaction ID: "64 hexadecimal characters"; verified automatically; shown in the pull request description (already public on-chain). For `remove`, the transaction ID that created the entry |
| `consent` | boolean | Yes for `add` | Must be `true`: the submitter is the person named or has that person's permission; recorded in the pull request body |
| `website` | string | No | Hidden honeypot; must be empty |

Derived on the server: entry `id` = first 12 hex characters of SHA-256 over lower-cased name, link, and image hash; branch `submission/<first 16 hex characters of the transaction ID>` (so one donation can only ever have one open pull request); labels `sponsor-submission` and `donation-verified`.

### Donation claim — `data/donations/<txid>.txt`

Created by the submission pull request, one per donation transaction; its content is the entry `id` it backs. A claim exists on the `sponsors` branch once merged; a closed-unmerged pull request releases the transaction. A removal request is accepted only if this file exists for the transaction ID supplied, and removes the entry it names; the claim file itself stays so the transaction can never be reused (the branch validator therefore allows a claim whose entry has been removed, and a second removal request finds a claim but no entry and opens nothing).

### Submission result (to the wallet)

| State | Meaning | Wallet shows |
|-------|---------|--------------|
| `created` | Pull request opened | "Submitted, awaiting review" |
| `duplicate` | Identical submission already open | "Already submitted, awaiting review" |
| `invalid` (with field list) | A rule failed | Which fields to fix |
| `not_verified` (with reason: `not_found`, `too_few_confirmations`, `wrong_recipient`, `below_minimum`) | Donation check failed | Why the donation was not accepted; for too few confirmations, try again shortly |
| `already_used` | This transaction already backs an entry or an open pull request | Donation already used |
| `rate_limited` | Visitor over 3/hour | Try again later |
| `queue_full` | 50 open submission pull requests | Try again later |
| `unavailable` | GitHub or server problem | "Could not be sent, try again later" |

## Runtime in the wallet (browser only)

- **SponsorEntry** (validated): `Name`, `ImageUrl?`, `Link?`. Built only from entries passing all rules; invalid entries dropped individually.
- **SponsorList**: `Entries` (newest first, deduplicated, capped at 1,000), `FetchedAt`, `SkippedCount`.
- **Last-good copy** (local storage): raw list text + `FetchedAt`; written only after a fully valid parse; read only when a fresh fetch fails; no wallet or user data.
- **SponsorLoadResult**: `Fresh`, `FreshEmpty`, `Stale`, `Unavailable` (same meanings as before; see [contracts/hosting-and-ui.md](contracts/hosting-and-ui.md)).

## Lifecycle

1. Visitor submits → server validates → server checks the donation on the explorers and that the transaction is unused → bot opens pull request on `submission/<txid prefix>`.
2. Maintainer reviews the entry → merge into `sponsors` (or close unmerged → entry never appears and the transaction is free again).
3. `build-sponsors-index` regenerates `sponsors.json` → wallet shows it within 10 minutes.
4. Removal: removal submission with the original transaction ID → server finds the claim file → pull request deleting the entry and image files → merge → regenerated list drops it.

## Identity and uniqueness

- Entry identity: `id` (hash of content). One donation transaction backs at most one entry (the donation claim).
- Duplicate in the list (display): same name (case-insensitive) + link + image; first wins.
